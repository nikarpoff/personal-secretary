# Люди в Obsidian и контекст встреч

Справочник состоит из обычных Markdown-карточек в `Secretary/People`. Каждую можно
открыть отдельной вкладкой Obsidian на Windows и Android; синхронизация и резервирование
используют уже настроенный vault. Дополнительный плагин Obsidian не требуется.
В Telegram отдельный экран контактов не добавляется: ассистент работает через MCP.

У карточки есть постоянный UUID, имя в `title`, необязательные варианты имени `aliases`
и свободный текст с контекстом знакомства, контактами и связанными людьми. Агент ищет
небольшую подборку, затем читает выбранную карточку или раздел. Справочник целиком не
загружается в память OpenClaw и не передаётся модели при каждом сообщении.

## Формат карточки

Ниже вымышленный пример документации, не созданная запись пользователя:

```markdown
---
id: 784e9797-dfb3-4a93-8ec2-e591c2f5f89f
type: person
status: open
title: Алексей Примеров
aliases: [Алексей из мастерской, Лёша Примеров]
created_at: '2026-11-02T12:00:00+03:00'
updated_at: '2026-11-02T12:00:00+03:00'
tags: [работа]
---
## Контекст знакомства
Обсуждали проект мастерской. Это вымышленный пример.

## Контакты
Не указаны.

## Связанные люди
Не указаны.

## Встречи и договорённости
Нет сохранённых договорённостей.
```

Через инструменты `aliases` задаются для карточек людей: до 8 непустых вариантов по 80 символов без
переносов строк. Имя и варианты имени участвуют в поиске. Одинаковые имена у разных
людей допустимы: агент должен уточнить человека, а не считать совпадение доказательством.
`due_at` и `remind_at` остаются полями задач; карточка человека сама по себе не напоминает.

Связь с другим человеком можно описать текстом и добавить обычную Markdown/Obsidian-ссылку
на его существующую карточку. Создаваемые сервисом имена файлов основаны на UUID; для
такой карточки подходит `[[<UUID>|Имя человека]]`. После ручного переименования файла
используйте его текущий путь в ссылке. Не копируйте один UUID в разные карточки.

## Инструменты и сообщения боту

Для справочника используются существующие инструменты:

| Действие | Вызов |
|---|---|
| Создать карточку | `create_note(kind="person", title=..., body=..., aliases=[...])` |
| Получить короткий контекст по имени/варианту имени | `get_note_context(kind="person", query=...)`, до 3 выдержек в одном ответе до 4000 символов |
| Явно поискать карточки шире | `search_notes(kind="person", query=..., limit=5)` |
| Прочитать выбранный контекст | `read_note(note_id=..., section=...)`, максимум 4000 символов |
| Изменить имя/варианты/текст | `update_note(note_id=..., expected_version=..., aliases=[...])` |
| Дополнить договорённости | `append_note` с текущей версией |
| Архивировать карточку | `archive_note` с текущей версией |

Примеры просьб:

- «Запомни: Алексей Примеров — знакомый из мастерской; называю его Лёшей Примеровым».
- «Что мы записали про Алексея из мастерской?»
- «Поставь встречу с Алексеем из мастерской завтра в 15:00».

Последнюю просьбу агент сначала соотносит с карточкой через один `get_note_context`,
если актуальных сведений ещё нет в диалоге. Короткий список не доказывает уникальность
совпадения. Если кандидатов несколько или данных недостаточно, он уточняет человека.
При необходимости конкретного факта читает выбранный фрагмент карточки. Если карточки нет, он не выдумывает биографию
и не объединяет людей только по похожим именам. Новая карточка создаётся по просьбе
владельца и из сообщённых им сведений; поиск в интернете не заполняет её автоматически.
Встречу по просьбе владельца можно создать с указанным им именем и без `person_ids`,
если подходящей карточки пока нет: справочник не должен мешать обычному планированию.

## Связь с календарём

`create_event` и `update_event` принимают необязательный `person_ids`: до 10 UUID
карточек людей. Сервис проверяет, что новые ссылки указывают на существующие неархивные
карточки `person`. Список событий возвращает эти UUID, после чего агент может прочитать
выбранные карточки. При обновлении пропущенное поле сохраняет ссылки, а `person_ids: []`
снимает их. Для события, не связанного с людьми, список пуст.

В Google Calendar сохраняются только UUID в
`extendedProperties.private.secretary_people`. Это метаданные копии события в выбранном
календаре, а не список участников Google. Связь не отправляет приглашений и не копирует
телефон, биографию или контакты в описание встречи. Типы private/shared и ограничения
этих свойств описаны в [официальной документации Google Calendar](https://developers.google.com/workspace/calendar/api/guides/extended-properties).

Название встречи и прочие явно переданные поля всё так же попадают в Calendar. Не считайте
private-метаданные отдельным хранилищем секретов: администратор и приложения с доступом к
этой копии календаря могут их прочитать. Чувствительные сведения остаются в карточке.

Переименование карточки сохраняет UUID, поэтому не требует изменения существующих связей.
Архивирование не переписывает календарь: исторический UUID остаётся, а карточку можно
прочитать для контекста. Заново связать архивную карточку нельзя. Если файл отсутствует,
повреждён или его UUID дублируется, агент сообщает о проблеме и не подставляет другого
человека. Старые встречи без `person_ids` не изменяются автоматически.

Карточки используют существующую проверку версии и сохранение конфликтов Markdown.
Обновление Calendar сохраняет прежний механизм GET + PUT: одновременные правки события
разными клиентами могут перезаписать друг друга; отдельная защита от таких конфликтов
в эту версию не добавляется.

## Обновление VPS

Нужны обновлённые backend и навык secretary. При инициализации backend создаёт People
внутри разрешённой Secretary; mount, WebDAV и `.env` остаются прежними. Подготовить каталог
вручную можно командой `mkdir -p data/obsidian/Secretary/People` на VPS, если используется
стандартный путь. Навык подключается read-only mount из репозитория в workspace шлюза;
ручное копирование не нужно. Для добавления mount пересоздайте шлюз по
[инструкции README](../README.md#3-openclaw), затем отправьте боту `/new`.
Команды развёртывания в рамках этих изменений не выполнялись.

Существующие карточки без `type: person` автоматически не переклассифицируются. Для ручного
переноса добавьте требуемое frontmatter и уникальный UUID, разместите файл в People и
синхронизируйте vault. При редактировании сохраните правила [версий и конфликтов](obsidian.md#версии-файлов-и-конфликты).
