# Obsidian на VPS: заметки, задачи и синхронизация

Это инструкция для последующего развёртывания. При подготовке изменений приложение,
контейнеры и тесты не запускались; подключения к рабочим Telegram, Google и Whisper не было.
Команды ниже выполняет владелец на VPS после проверки конфигурации и резервной копии.

## Хранение и границы доступа

```text
data/
├── obsidian/                         # один полный vault
│   ├── Secretary/                    # единственная область заметок для Python
│   │   ├── Inbox/
│   │   ├── Tasks/
│   │   ├── Ideas/
│   │   ├── Knowledge/
│   │   ├── People/                   # карточки людей и контекст встреч
│   │   ├── Archive/
│   │   └── .secretary-history/        # служебные предыдущие версии, не читать через MCP
│   ├── Personal/                     # только Obsidian/WebDAV, не ассистент
│   └── .obsidian/                    # локальная конфигурация клиента, обычно не синхронизировать
├── assistant-state/                  # отметки доставки, конфликты; не часть vault
├── openclaw/                         # workspace и состояние шлюза, без vault
└── webdav/                           # сертификаты Caddy и private/webdav.yaml (секрет WebDAV)
```

`OBSIDIAN_VAULT_DIR` по умолчанию равен `./data/obsidian`. Backend получает только
`<OBSIDIAN_VAULT_DIR>/Secretary` как `/notes` и отдельный `/assistant-state`.
WebDAV получает полный vault. У OpenClaw нет mount ни vault, ни assistant-state;
заметки доступны модели только через MCP. SQLite, эмбеддинги и векторный поиск не используются.

WebDAV-сервисы включаются профилем `obsidian-sync`. Их отдельная Docker-сеть не соединяет
WebDAV со шлюзом или backend. Снаружи публикуется HTTPS через Caddy; порт WsgiDAV `8080`
не публикуется. Backend и OpenClaw сохраняют публикацию своих портов на `127.0.0.1`.

## Точное соответствие путей Remotely Save

В стандартной конфигурации Remotely Save добавляет имя локального vault к адресу WebDAV.
В [исходнике плагина](https://github.com/remotely-save/remotely-save/blob/master/src/fsWebdav.ts)
база вычисляется как `remoteBaseDir || vaultName`, затем используется путь `/<base>/`.
Поэтому здесь root WebDAV — `/var/lib/dav`, а bind полного vault расположен в
`/var/lib/dav/${OBSIDIAN_VAULT_NAME}`.

При значениях по умолчанию соответствие такое:

| Место | Путь |
|---|---|
| Полный vault на VPS | `./data/obsidian/` |
| Корень WebDAV | `https://notes.example.com/` |
| Папка vault на WebDAV | `https://notes.example.com/Obsidian/` |
| Полный vault внутри WebDAV-контейнера | `/var/lib/dav/Obsidian/` |
| Заметка клиента | `Secretary/Ideas/<id>.md` |
| Та же заметка в Python-контейнере | `/notes/Ideas/<id>.md` |

На Windows и Android назовите локальные vault одинаково, например `Obsidian`, и укажите
WebDAV endpoint **`https://notes.example.com/`**, без добавления `/Obsidian/` вручную.
Иначе получится двойная вложенность `/Obsidian/Obsidian/`. Если локальное имя отличается,
задайте в Remotely Save **Change the remote base directory** равным `OBSIDIAN_VAULT_NAME`.
Это имя также используется в ссылках `obsidian://open?vault=...`, поэтому одинаковые
локальные имена удобнее. После смены имени не создавайте новую пустую удалённую базу поверх
данных: сначала проверьте каталог и резервную копию.

## Подготовка Linux VPS

Не перезаписывайте существующий `.env` примером. Добавьте только новые настройки:

```dotenv
OBSIDIAN_VAULT_DIR=./data/obsidian
OBSIDIAN_VAULT_NAME=Obsidian
NOTE_REMINDER_POLL_SECONDS=30
OBSIDIAN_SYNC_DOMAIN=notes.example.com
```

Для notes требуется непустой `AUTH_TOKEN`. Compose задаёт `NOTES_ROOT=/notes` и
`ASSISTANT_STATE_DIR=/assistant-state`. Вне Compose эти два пути опциональны и задаются вместе.
В первой версии изменение заметок рассчитано на Linux-файловую систему с `renameat2`;
при отсутствии безопасной атомарной операции запись прекращается с ошибкой.

Подготовьте каталоги и отдельный секрет WebDAV:

```bash
mkdir -p data/obsidian/Secretary/{Inbox,Tasks,Ideas,Knowledge,People,Archive}
mkdir -p data/obsidian/Personal data/assistant-state data/webdav/{caddy-data,caddy-config,private}
cp deploy/webdav/wsgidav.example.yaml data/webdav/private/webdav.yaml
chmod 700 data/webdav/private
chmod 600 data/webdav/private/webdav.yaml
chmod 700 data/assistant-state
```

В `data/webdav/private/webdav.yaml` замените пользователя `secretary-sync` и пароль
`REPLACE_WITH_A_LONG_UNIQUE_PASSWORD`. Пароль должен быть отдельным от `AUTH_TOKEN`,
Telegram и шлюза. Эта конфигурация хранит пароль открытым текстом на VPS, поэтому файл
доступен только администратору и WebDAV-контейнеру, исключён из Git и образов и входит
только в зашифрованные резервные копии. Никаких анонимных пользователей в шаблоне нет.
Конфигурация лежит вне `secrets/`, чтобы её не получил backend с существующим mount Google secrets.

WsgiDAV и существующий backend используют стандартного пользователя своих образов
(в текущей конфигурации root внутри контейнера), чтобы не изменить права существующих
Google secrets. При самостоятельном переходе на непривилегированного пользователя обоим
сервисам нужны согласованные UID/GID и права на bind mounts; не делайте vault общедоступным
через `chmod 777`. WebDAV получает `read_only` root filesystem, `cap_drop: ALL` и
`no-new-privileges`; запись разрешена в смонтированный vault и ограниченный `/tmp`.

Для Caddy нужен домен с A/AAAA, направленными на VPS, доступные TCP-порты `80` и `443`
и постоянный каталог сертификатов. Не оставляйте неправильную AAAA-запись. Если на этих
портах уже работает reverse proxy, используйте его для этого домена вместо второго Caddy;
сохраните HTTPS, Basic auth на WsgiDAV, все DAV-методы и неизменённые пути. Не публикуйте
`8080` напрямую и не передавайте логин/пароль по HTTP. Требования автоматического TLS
описаны в [документации Caddy](https://caddyserver.com/docs/automatic-https).

После подготовки и отдельного решения о развёртывании:

```bash
docker compose up -d --build personal-assistant
docker compose --profile obsidian-sync up -d --build obsidian-webdav obsidian-https
```

Команды здесь приведены как инструкция и в рамках изменения проекта не выполнялись.
Связка WsgiDAV/Caddy сверена по документации и исходникам, но реальная совместимость
выбранных версий клиентов, TLS и VPS без запуска не проверена. Первую синхронизацию
проводите на небольшой копии vault с отдельной резервной копией.

## Windows и Android

1. Создайте локальный vault `Obsidian` в Obsidian на Windows. На Android создайте отдельный
   локальный vault с тем же именем. Не открывайте WebDAV как сетевую папку вместо локального vault.
2. На каждом устройстве установите community plugin **Remotely Save**. Выберите remote service
   **WebDAV**, endpoint `https://notes.example.com/`, пользователя и пароль из секретного файла.
   Authentication type — **Basic**; проверка сертификата должна оставаться включённой.
   Для **Depth Header Sent To Servers** выберите `only supports depth='1'`:
   плагин выполнит обход обычными DAV-запросами без требования `Depth: infinity`.
3. Проверьте отображаемую remote base directory: `Obsidian`. Выполните встроенную проверку
   подключения. Начальную загрузку существующих данных делайте с одного выбранного устройства;
   затем подключайте второе. Не начинайте с двух различающихся полных копий одновременно.
4. Не включайте шифрование Remotely Save для этой схемы: Python должен читать обычный Markdown
   на VPS. HTTPS шифрует транспорт; резервные копии шифруются отдельно. Для Personal с отдельным
   E2EE нужен другой vault/отдельная синхронизация, это не первая версия.
5. Оставьте синхронизацию `.obsidian` выключенной. Служебная `.secretary-history` скрытая;
   в **Regex Of Paths To Ignore** добавьте регулярное выражение
   `^Secretary/\.secretary-history(?:/|$)` (это regex, а не glob).
   Не включайте глобальную синхронизацию скрытых служебных файлов.
6. Перед редактированием на другом устройстве синхронизируйте изменения. После редактирования
   снова выполните sync и дождитесь результата. Не совмещайте Remotely Save с другой программой
   синхронизации этой же папки.

Плагин не обеспечивает фоновый системный sync при закрытом Obsidian. На Android приложение
может быть приостановлено ОС; откройте его, запустите синхронизацию и дождитесь завершения.
Сохранённая офлайн-задача станет известна VPS и сможет напоминать только после загрузки на сервер.
Разрешение работы в фоне не превращает community plugin в отдельную Android-службу.
Поведение scheduled sync и конфликтов описано в
[README Remotely Save](https://github.com/remotely-save/remotely-save#scheduled-auto-sync).

Синхронизация передаёт изменения и удаления и не заменяет резервирование. Бесплатный Remotely Save
при конфликте выбирает версию по своей политике; автоматическое слияние не гарантируется.
История сервиса защищает его собственные записи и сохраняет конфликтные версии, но не превращает
несколько офлайн-клиентов в транзакционную файловую систему. Проверяйте sync log и не редактируйте
одну заметку одновременно на нескольких устройствах.

## Формат Markdown

Одна запись — один обычный UTF-8 `.md` с небольшим YAML frontmatter. Минимальный пример задачи:

```markdown
---
id: 3bd3fa97-ce82-41c7-8b0b-7de4066fe1cf
type: task
status: open
title: Позвонить в сервис
created_at: '2026-11-02T12:00:00+03:00'
updated_at: '2026-11-02T12:00:00+03:00'
tags: [дом]
due_at: '2026-11-04T18:00:00+03:00'
remind_at: '2026-11-04T10:00:00+03:00'
---
Уточнить готовность заказа.
```

`id` — стабильный UUID: при переносе или переименовании файла не меняйте его и не копируйте
одинаковый id в разные заметки. `type` принимает `note`, `task`, `idea`, `knowledge`, `person`, статус —
`open`, `done`, `cancelled`, `archived`. Начальные каталоги соответствуют типам: Inbox, Tasks,
Ideas, Knowledge, People. Архивирование сохраняет UUID и переносит запись в Archive.
Заголовок `title` обязателен; H1 в теле можно добавлять по желанию.

Для `type: person` поле `aliases` хранит до 8 вариантов имени по 80 символов. Карточки
ищутся по имени и этим вариантам, а затем читаются выбранными фрагментами. Формат и привязка
встреч по `person_ids` описаны в [справочнике людей](people.md). Каталог People создаётся
backend при инициализации внутри уже существующего mount Secretary; новые mounts не нужны.

`created_at` и `updated_at` обязательны; `tags` — список до 16 тегов по 40 символов.
`due_at` и `remind_at` необязательны и разрешены только для задач. Без явного смещения время
интерпретируется в `TIMEZONE`. Для этих полей нужна дата **и время**: если владелец назвал
только день или сказал «потом», ассистент уточняет время и не выдумывает срок.
Идея без срока остаётся идеей, не становится просроченной задачей.
Markdown-checkbox в теле не изменяет статус автоматически: для завершения нужно изменить
`status: done` в Properties/frontmatter либо попросить ассистента.

Неподдерживаемые/некорректные файлы пропускаются отдельно, диагностика показывает их количество.
Заметки без нужного frontmatter не импортируются автоматически. Первая версия не переписывает
все существующие документы и не восстанавливает старую SQL-реализацию. Для ручного переноса
выберите нужные файлы, добавьте метаданные с уникальными UUID и разместите их в Secretary.

## Контракт инструментов и объём контекста

| MCP-инструмент | Поведение |
|---|---|
| `get_note_context` | Ключевые слова темы длиной 1–200 символов, необязательные `kind`/`tag`; до 3 релевантных выдержек, весь компактный JSON до 4000 символов с метаданными; без Archive и только открытые задачи |
| `search_notes` | Лексический поиск/фильтры, максимум 5 результатов, короткие выдержки; Archive исключён по умолчанию |
| `read_note` | Выбранный UUID, раздел либо фрагмент до 4000 символов; возвращает версию и источник |
| `create_note` | Создание Markdown, включая `kind: person` с вариантами имени `aliases`; короткая квитанция |
| `append_note` | Дополнение выбранной записи с `expected_version` |
| `update_note` | Изменение переданных полей/статуса с `expected_version`; явные `clear_due_at`/`clear_remind_at` очищают время |
| `archive_note` | Архивирование одной записи с `expected_version`, без постоянного удаления |
| `notes_status` | Время сервера и состояние индекса/доставки без содержимого vault |

Пути не являются аргументом инструментов: используется UUID. Сервис ограничивает каталоги,
размер файлов и выдачи, запрещает симлинки и выход за Secretary. В первой версии максимум файла
128 КиБ, тела при записи через файловый модуль 32000 символов (MCP принимает до 16000 символов
за вызов), выдержки `search_notes` — 240 символов. Индекс ограничен 5000 файлами, 20000 записями каталогов,
глубиной 8 и 32 МиБ исходных байтов; память для декодированного текста и метаданных расходуется
дополнительно. При превышении лимитов поиск помечается как неполный, чтение по id, изменения
и напоминания блокируются до уменьшения области Secretary. Эти ограничения проверяются
сервисом, а не обещанием модели. Серверный индекс локальный, без LLM; содержимое всего vault
не отправляется модели на каждом запросе.

Для обычного вопроса о проекте, прежнем решении или человеке ассистент сам выполняет один
`get_note_context`, если сохранённые сведения могут помочь и актуальных фактов ещё нет в диалоге.
В запрос передаются короткие ключевые слова темы, без полной переписки. Python локально выбирает
до трёх лексически релевантных выдержек длиной до 600 символов каждая. Весь сериализованный
JSON-ответ ограничен 4000 символами, включая UUID, заголовки, ссылки, статус, версию и сроки/время
напоминаний задач. Archive исключён; из задач берутся только записи со статусом `open`.
Для подбора не нужны вызовы LLM, интернет или дополнительные агенты.
Подбор учитывает совпадения отдельных слов в названии, вариантах имени, тегах и тексте,
сначала предпочитая точное название/вариант имени и больше совпавших слов. Нормализованный
текст кешируется по версии файла. Это лексический поиск, который может пропустить синонимы
и другие словоформы. Индекс использует существующий кеш до 3 секунд; выбранные файлы
перечитываются перед выдачей. `offset` указывает начало фрагмента в теле заметки, `truncated`
отмечает неполный текст, `has_more` — невыданные совпадения, а `index_truncated` — неполный индекс.
При неполном индексе новый инструмент не выдаёт выдержки, сохраняя ограничение чтения по UUID.

Приветствия, обычное общение, простое сохранение новой записи, просмотр календаря и утренняя
сводка такой поиск не запускают. Для обычного вопроса навык задаёт один вызов без повторных
поисковых циклов. Дополнительный `read_note` нужен только ради конкретного недостающего факта
либо перед изменением выбранной записи; для явной просьбы поискать шире/глубже остаются
`search_notes` и чтение выбранных фрагментов. Карточки людей не связываются со встречами при
неясной идентичности: ассистент уточняет человека, а не делает вывод по короткому списку.
При пустой или неполной выдаче он сообщает о недостатке сведений.

Предел 4000 символов проверяет backend для одного ответа `get_note_context`. Он не ограничивает
суммарный контекст диалога; правило одного вызова задаёт навык. Индекс в RAM также не является
контекстом модели. Фоновые обходы, дайджесты и отдельные «архивариусы» не запускаются.

Ссылка на заметку имеет вид `obsidian://open?vault=Obsidian&file=Secretary%2F...` и работает на устройстве с
одноимённым локальным vault после синхронизации. Поддержка таких ссылок конкретным Telegram-клиентом
может отличаться; запись всегда можно найти в Obsidian по названию/id.

Файлы заметок не добавляются в workspace, AGENTS.md, MEMORY.md, bootstrap hooks или
автоматическую память OpenClaw. Нельзя поручать агенту многократно листать все страницы,
чтобы обойти лимиты. При ответе по заметкам он указывает использованные источники и явно
говорит, когда данных не хватает. Массовые изменения сначала показываются списком для
подтверждения; первая версия предоставляет только операции над одной записью.

В `openclaw.patch.json5` используются `tools.profile=messaging`, `read` для навыка и отдельно
разрешённые `web_search`/`web_fetch` для публичного интернета (см. [настройку поиска](web-search.md)).
Сохранены `tools.fs.workspaceOnly=true`, запрет runtime/мутаций файлов и `tools.elevated.enabled=false`.
`read` сохраняет доступ к `workspace/skills/secretary/SKILL.md`. Уменьшение списка инструментов
само по себе не является файловой песочницей: границу обеспечивают отсутствие mount vault в
шлюзе, проверка путей filesystem tools и файловый модуль backend.
Поддержка `workspaceOnly` проверена в
[схеме OpenClaw v2026.10.9](https://github.com/openclaw/openclaw/blob/v2026.10.9/src/config/zod-schema.agent-runtime.ts).
Docker sandbox для агентных команд здесь не включается: команды модели запрещены, Docker socket
в gateway не монтируется. Whisper CLI остаётся доверенным настроенным media-обработчиком.

Чтобы включить этот режим на существующем VPS, перенесите обновлённые исходники и выполните
в каталоге проекта:

```bash
docker compose up -d --build personal-assistant
mkdir -p data/openclaw/workspace/skills
cp -r openclaw/skills/secretary data/openclaw/workspace/skills/
sudo chown -R 1000:1000 data/openclaw/workspace/skills/secretary
docker compose restart openclaw-gateway
scripts/openclaw.sh mcp probe personal-assistant
scripts/openclaw.sh skills info secretary
```

Backend нужно пересобрать для нового MCP-инструмента, а навык 1.4.0 скопировать в существующий
workspace. Перезапуск шлюза обновит навык и список MCP-инструментов. Новые переменные
окружения и зависимости не нужны; vault не переносится в OpenClaw.
Команды приведены для владельца и при подготовке изменения не выполнялись.
Перед применением полного патча установите и включите DuckDuckGo по
[инструкции поиска](web-search.md), затем подставьте Telegram id.
На развёрнутом шлюзе владелец может затем проверить `scripts/openclaw.sh config validate` и
`scripts/openclaw.sh security audit`. Для фактического контекста в Telegram доступны `/status`,
`/context list`, `/context detail`, `/usage tokens`; `/context detail` показывает также размер схем
инструментов. Это диагностика для эксплуатации, при подготовке изменений она не запускалась.
Команды сверены с [документацией контекста OpenClaw v2026.10.9](https://github.com/openclaw/openclaw/blob/v2026.10.9/docs/concepts/context.md).

## Версии файлов и конфликты

`expected_version` — SHA-256 текущих байтов файла, а не только `updated_at`. Перед изменением
сервис повторно читает файл и сравнивает версию. Изменившийся файл не перезаписывается молча:
предложенная правка сохраняется для разбора конфликта, инструмент сообщает об ошибке конфликта.
Нужно прочитать текущую запись и согласовать слияние, не повторять старую запись автоматически.

На Linux атомарная замена через `renameat2` сохраняет вытесненную предыдущую версию в
`Secretary/.secretary-history`, в том числе её inode при уже открытой внешней записи.
Метаданные конфликтов находятся в `assistant-state/conflicts`. Эти каталоги не выдаются
через MCP. Не удаляйте историю, пока выполняется синхронизация: в первой версии автоматической
очистки истории нет. Контролируйте свободное место, резервируйте историю и очищайте только
после остановки писателей и проверки нужных версий. Синхронизация с внешними офлайн-клиентами
всё равно не гарантирует автоматическое слияние и строгое compare-and-swap на стороне клиента.

## Напоминания задач

Python проверяет открытые задачи с `remind_at` раз в `NOTE_REMINDER_POLL_SECONDS`, без LLM и
без Google Calendar. `due_at` — только срок: он не создаёт уведомление автоматически.
Завершение, отмена и архив исключают задачу из отправки; перенос `remind_at` создаёт новый
ключ доставки. Повторное открытие задачи с тем же уже доставленным `remind_at` не отправляет
его снова: для нового уведомления задайте новое время.

Отметки и попытки находятся в `assistant-state/task-reminders.json`. Ключ — UUID плюс время
напоминания в UTC. Попытка фиксируется до отправки, успешная доставка — после ответа Telegram.
Ошибки повторяются с увеличивающимся интервалом до 15 минут; при перезапуске задержка и
доставленные отметки сохраняются. Просроченное `remind_at` открытой задачи доставляется после
восстановления, поэтому старые ненужные задачи нужно завершить/отменить/перенести.

Точно однократную доставку Telegram не гарантирует: между приёмом сообщения и сохранением
отметки возможен дубль после аварии; сетевой таймаут после фактического приёма также неоднозначен.
Если состояние повреждено, недоступно или занято другим процессом, отправка останавливается
вместо бесконечных неотмеченных повторов. Не удаляйте файл состояния для «починки» без копии:
это может вызвать повторную отправку старых задач. `notes_status` показывает блокировку/ошибку.
Без Telegram отметки доставки не выставляются. Перед отправкой состояние задачи перепроверяется,
но изменение уже после начала HTTP-запроса не может отозвать принятое Telegram сообщение.

Повторные попытки имеют задержку 30, 60, 120, 240, 480, затем максимум 900 секунд;
за один проход выполняется до 50 отправок. Отметки активных задач сохраняются, отметки исчезнувших
или изменённых ключей очищаются после 90 дней. Состояние ограничено 20000 отметками и 8 МиБ;
превышение останавливает отправку. После ручного возврата очень старого `remind_at`, чья отметка
уже очищена, возможно новое уведомление. Диагностика показывает последние ошибки доставки
и количество ожидающих попыток. `/health` остаётся проверкой живого HTTP-процесса;
для контроля задач используйте `notes_status`.

Один каталог состояния обслуживается одним scheduler. Не запускайте несколько backend workers
или реплик с отдельными копиями state для одного vault. Календарные напоминания сохраняют прежнюю
логику и RAM-отметки; постоянные JSON-отметки относятся к задачам Obsidian.

## Резервирование и восстановление

Синхронизация не резервная копия. Делайте независимую версионную зашифрованную копию полного
vault, включая `.secretary-history`, `assistant-state`, `data/openclaw`, настроек развёртывания и
`secrets/`, а также `data/webdav` с отдельным секретом и ключами Caddy.
Храните хотя бы одну копию вне VPS, несколько поколений и ограничьте доступ к ключам.
Сам `Personal` ассистенту не виден, но доступен WebDAV и администратору VPS и должен резервироваться.

Для согласованного снимка приостановите sync на клиентах и остановите WebDAV и backend либо
используйте согласованный snapshot файловой системы. Копирование только `.md` при продолжающихся
записях может оставить неполные файлы и несогласованные отметки. Состояние Caddy содержит приватные
ключи сертификатов и тоже требует защиты. Периодически проверяйте восстановление в отдельный каталог,
не поверх рабочего vault.

При восстановлении сначала остановите писателей, восстановите vault и assistant-state одного
снимка, проверьте пути/владельцев и только затем подключайте клиентов по одному. Откат старого state
может повторить уже отправленные сообщения; восстановление vault без state теряет дедупликацию.
Отключённый профиль WebDAV не удаляет bind mounts. Не удаляйте data/ для обновления образов.
